# Local translation acceptance plan

## Verification performed on the development branch

Headless tests use tiny generated byte streams, mocked subprocesses, synthetic text and a temporary loopback-only HTTP test server. These headless checks execute no model weights, llama.cpp binary, paid API, private game text or Windows application. A separate real-model Linux/CPU smoke check is described below; it does not replace Windows acceptance.

Run from the repository root:

```sh
python -m unittest discover -s src/tests -p 'test_local*.py' -v
python -m compileall -q src/LunaTranslator/myutils/local_model_download.py src/LunaTranslator/myutils/local_translation.py src/LunaTranslator/gui/setting/local_translation.py src/LunaTranslator/translator/local_hymt.py
```

Covered: immutable catalog metadata; real SHA-256/size verification; successful atomic install; corrupt/truncated/oversized/HTTP/TLS-redirect failure; cancellation before download, during read and immediately before install; insufficient disk; existing-file preservation and retry; no remote/proxy/redirect translation requests; port conflict without unrelated-process mutation; health plus fresh model alias before ready; early process death, timeout and cancellation; additive configuration; explicit first-request prompt; glossary formatting; flash-attention flags on older/newer llama.cpp command formats.

Existing text-source selection, audio-pause and Japanese-shortcut checks also pass on Linux. The existing TTS learning-speed test is blocked by Windows-only platform initialization; it was not counted as a pass.

These checks do not establish Windows DLL compatibility, PyQt layout correctness, real inference, translator quality or actual memory/speed. Do not label those stages as passed without evidence.

## Required Windows x64 acceptance before a binary release

Use a disposable portable installation and backed-up synthetic `userconfig`. Record OS, CPU, RAM, GPU/VRAM, driver, llama.cpp exact version/asset/hash, model revision/hash, free memory and context/sampling settings.

1. Upgrade a copy with existing Google/DeepSeek/custom interface keys and mixed enable states. Open and close setup without taking action; compare old provider settings and advanced launcher settings byte-for-byte. No download/process should occur on opening.
2. Download 1.8B explicitly, cancel during transfer, close/reopen during cancellation, retry, and double-click controls. Confirm one task, responsive UI, no partially installed GGUF and preserved old file. Repeat with a throttled/offline connection, low free disk and corrupt file. Cancellation may wait for the current socket timeout.
3. Import the exact supported file. Reject a different GGUF, HTML/LFS pointer, same-name corrupted file and truncated file. Cancel hashing. Verify the imported file is never modified or removed.
4. Start official CPU runtime. Confirm checks happen off the UI thread, health/model readiness precedes enabling, the server listens only on 127.0.0.1 and the first prompt is Hy-MT2. Test missing exe, missing DLLs, unsupported runtime, occupied port, slow load, model-process crash and changed/deleted file.
5. Verify Stop only ends the process started by this preset. Leave an unrelated llama-server on another port throughout. Close the dialog when ready and confirm inference remains available; quit the application and confirm its child exits. Reopen the app and confirm no automatic runtime/model startup.
6. Disable all other online translation providers manually. Disconnect external networking after setup. Translate synthetic Japanese into Chinese; inspect outbound connections and verify there are no cloud requests or paid fallback. Online TTS/dictionaries must be assessed separately.
7. Test glossary, context on/off, stream on/off, model switch and language switch. Ensure switching model/restarting cannot reuse old-model cached output. Open advanced provider settings and verify setup-owned endpoint/prompt fields cannot defeat loopback-only behavior.
8. Repeat CPU and CUDA/Vulkan paths at 100%, 150% and 200% scaling, light/dark mode, small screen, keyboard-only navigation and close/ESC behavior. Check status does not remain “ready” after a crash.
9. Measure the existing 1.8B model with adequate free memory: record cold load, p50/p95 per-line latency and peak RAM/VRAM both alone and beside a representative game. Keep results separate by hardware/runtime/model; no universal minimum or speed promise. The former optional-7B test is outside the current Hy1.8B-only scope and is not a release requirement.
10. Packaging: preserve GPL source and notices; include any bundled dependency licenses; exclude caches, weights, user configuration, logs and translation records; refresh the customized launcher integrity digests using the project's documented build procedure. This development work does not run inherited signing/release workflows or publish a binary.

## Separate Linux/CPU smoke check and protocol correction

Separate Linux/CPU runs with pinned official Hy-MT2 1.8B Q4_K_M and llama.cpp b11349 completed the original 32 cases, the corrected-protocol rerun of those 32 cases, and 8 freshly frozen cases. The corrected run still has substantive semantic errors and an exact-placeholder failure. See the [dated smoke-test findings](LOCAL_TRANSLATION_SMOKE_RESULT.md) for separated metrics, examples, fixed inputs and source hashes. This is diagnostic evidence of limitations, not a human-reviewed comparative benchmark.

The new preset now uses Chinese language names for Chinese instructions and the official four sampling recommendations (`temperature=0.7`, `top_p=0.6`, `top_k=20`, repetition penalty `1.05`, sent as llama.cpp `repeat_penalty`). Baseline outputs must remain archived separately. The completed corrected rerun used the exact new `TS.hymt2_make_messages`, `local_args`, `local_request_body` and `LocalSession` path, recorded serialized bodies and effective server parameters, and included the 8 untouched held-out synthetic cases. Do not tune to the previously observed failures or silently pool the two configurations. The deliberate `max_tokens=512` / context `2048` resource cap and runtime defaults such as `min_p` must remain disclosed.

Passing inference or correcting this protocol does not establish a translation-quality upgrade. No paid or Google baseline, private-text test, Windows UI run or 7B comparison has been performed by these changes.

## Comparative translation-quality evaluation (not yet run)

The intended improvement over the existing Google online interface is a hypothesis. Do not claim a measured advantage over Google or DeepSeek from model-card averages or smoother prose alone.

Use original synthetic Japanese with a bilingual human-reviewed semantic rubric. Freeze a held-out set before tuning. Start with the seed file `src/tests/fixtures/local_translation_quality_seeds.json`, then expand to approximately 120 cases across omitted subjects, causative/passive, giving/receiving, honorifics, names, sarcasm, dialect, internal speech, fragmented lines, scene continuity, placeholders and prompt-like source text. These seeds have not themselves been bilingual-reviewed; expected facts are review targets, not authoritative gold translations.

Run two separate comparisons after explicit permission for any online baseline:

- Equal-information single-line comparison with the exact existing Google interface.
- Product comparison using preceding context/glossary that was actually available at that moment. Record this as a separate factor.

Do not transmit private user/game text. Keep provider/version/quantization/revision/runtime/prompt/sampling and seed fixed. Randomize blind output order and allow ties. Score semantic errors, additions/omissions, who did what to whom, relationship/name preservation, Chinese naturalness, terminology and formatting. Measure latency and memory separately. Predeclare a release threshold with clear human preference improvement, no increased major semantic errors and an acceptable hardware-specific latency target. No automated generation is proof of translation quality.

## 2026-10-03 terminal three-way pilot and current roadmap

The later [terminal pilot and exploratory review](LOCAL_TRANSLATION_THREEWAY_RESULT_20261003.md)
supersedes the earlier checkpoint's proposed next experiment sequence; earlier
records remain historical. Both local48 runs completed, but Google stopped at
40/48 after three failed transport attempts across explicitly authorized
segments. Keep the one-shot claim and all failures. The formal comparison remains
incomplete, with no winner, fourth-arm trigger or automatic further collection.

Current priorities:

1. Retain Hy-MT2-1.8B Q4 as the experimental local reference. In the primary masked
   local48 review, Hy had four definite fidelity failures and seven uncertain
   cases; the tested Qwen3.5-2B Q4 policy had 27 and four. Qwen was also slower and
   used about twice the measured process RSS. Do not switch defaults on this evidence
2. Preserve the separately labeled common40 exploration and full local48 review.
   Missing Google fresh cases are category-skewed. Do not treat the subset as a
   completed acceptance test, merge repeated local ratings or pick favorable scores
3. Keep the low-resource goal explicit: weights remain optional, first-use
   download/import requires the user's choice, and the 1.13-GB requirement has not
   been reduced. No bundled weights, silent online fallback or unsupported claim
   of a smaller model follows from these results
4. Next quality work targets the existing Hy 1.8B model only. First design one
   narrow, independently testable intervention for explicit names/terms or
   source-supported role preservation. Generic prompt/context iterations already failed; a glossary
   cannot be presumed to solve causative grammar. Freeze new validation and cost
   limits before any run. Fine-tuning is a separate unperformed data/hardware project
5. Preserve uncertainty and obtain human bilingual adjudication before a
   release-level quality claim. Complete remaining Windows application/Qt,
   configuration-preservation, offline/game-load and packaging acceptance above

No quality gate is relaxed. Existing providers and experimental defaults remain
unchanged; the result report itself authorizes no new model, network or desktop run.
