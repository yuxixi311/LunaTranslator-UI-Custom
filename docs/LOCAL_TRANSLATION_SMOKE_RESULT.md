# 实验性 Hy-MT2 1.8B：真实模型初测结果

日期：2026-10-02（UTC）。结论：**Linux/CPU 上能实际加载和推理，但官方参数修正后仍有重大语义错误和占位符破坏。本预设仅作为低资源实验选项，不作为已验证的翻译质量升级推荐。**

## 测了什么

- 原开发预设 32 条合成文本；修正后重跑同 32 条，另测 8 条事先固定、未参与修正的合成文本。72 个非流式请求全部正常结束，但“请求成功”不表示翻译正确。
- Linux x64 / CPU；推理与批处理均限制 2 线程；上下文 2048、输出上限 512、单并发、seed 42、`cache_prompt=false`，未命中提示词缓存。
- 修正后的实际请求使用 `temperature=0.7`、`top_p=0.6`、`top_k=20`、`repeat_penalty=1.05`；中文指令使用“简体中文”。核查了序列化请求和服务端有效参数。
- 运行库默认 `min_p≈0.05`、`repeat_last_n=64` 未改变。它们不是模型卡给出的新建议。
- GGUF 内聊天模板与官方模板一致；真实本地 HTTP 传输和原有 Sakura 流式解析器也完成了额外流式检查，响应正常关闭，示例译文与非流式一致。

## 速度和内存：仅限此次短句、环境与设置

| 分组 | 条数 | 中位延迟 | P95（最近秩） |
|---|---:|---:|---:|
| 原开发预设 | 32 | 1.046 秒 | 1.754 秒 |
| 修正后，同 32 条 | 32 | 1.095 秒 | 1.749 秒 |
| 修正后，另外 8 条 | 8 | 1.109 秒 | 1.776 秒 |

修正后 40 条的输入约 31–99 tokens、输出约 7–23 tokens；采样到的模型服务进程峰值 RSS 约 **2.05 GiB**。这是服务进程占用，不是整个翻译器加游戏的总内存。约 1.55 秒到健康状态的启动时间是在模型下载/校验已预热文件缓存之后测得，**不是冷盘启动时间**。

这些结果不能推算低端笔记本、Windows、GPU、长文本或与游戏/OCR 同时运行的表现，也不是不同模型的速度比较。

## 修正后仍出现的错误（合成文本摘录）

- `私は先輩に、みんなの前で歌わされた。` → `我在前辈面前，在大家面前被演唱了。`：丢失“被前辈要求/迫使唱歌”的使役关系
- `謝ってくれたとしても、鍵を返すつもりはない。` → `就算他们表示感谢，我也不打算归还钥匙。`：把道歉误为感谢
- `HPが{hp}以下になると` → `当HP低于{hp}时`：丢失“等于”这一边界
- 新增样本 `今日中に返さなくてもいいけれど、なくさないでね。` → `今天不必立刻归还，但请不要不归还。`：把“别弄丢”改成归还义务
- 新增样本中的 `{minutes}` 被译成 `{分钟}`：未保持占位符标识

也有普通句、给受关系、术语和部分上下文样例正确，但不足以抵消上述实质错误。测试文本与评判未经日中双语人工基准评审；这里不提供总体准确率，不把这些样本错误数推断为实际游戏中的错误率。未针对已见失败样本继续调参。
