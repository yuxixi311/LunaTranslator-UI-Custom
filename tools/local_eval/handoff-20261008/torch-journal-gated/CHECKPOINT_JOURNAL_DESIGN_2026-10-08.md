## Deterministic journal format and schedule

Create `work/download-progress.journal` once using exclusive binary creation (`xb`, unbuffered). Hold that handle until finalization. Never reopen, replace, truncate, rename, rotate, resume or retry this journal in an attempt. Exclusive creation means create-if-absent, not a claim of Windows denial-of-sharing locking.

The file starts with exactly eight bytes `LTJR0001`. Each frame contains a four-byte unsigned big-endian payload length L, L bytes of UTF-8 compact JSON, then 32 digest bytes. Require 1 <= L <= 2,048. Frame digest is SHA-256(previous_digest || length_bytes || payload_bytes); previous_digest is 32 zero bytes for sequence 0. JSON uses sorted keys, compact separators, ASCII escaping, and rejects NaN, duplicate keys and unknown schema fields on read. Digests detect damage and bind sequence; they are not authentication against a malicious writer.

Every payload has fixed schema/version, runtime candidate ID, runtime source SHA-256, sequence, event, request_count, get_send_attempts, http_status, received_bytes, written_bytes, actual_sha256, counters_complete, response_body_complete, sha256_matches_expected, status, and first_error (null or the existing bounded diagnostic projection). Do not copy arbitrary exception text, paths, secondary diagnostics, clock strings or the entire expanding state into frames. Retain complete state and bounded secondary diagnostics for the separate terminal JSON. Serialization exceeding 2,048 bytes fails closed; tests must exercise maximum permitted field lengths. Strict types reject bool-as-int counters. Counters satisfy 0 <= written <= received <= BODY_MAX and never decrease. Sequence starts at zero and increments by one.

Events, each emitted at most once except BYTE_SNAPSHOT:

1. INITIAL after disk preflight and before any network activity
2. REQUEST before initiating the sole GET, after request_count becomes 1
3. SENT at the existing on_send hook, after get_send_attempts becomes 1
4. HEADERS after the response status is known
5. BYTE_SNAPSHOT only after a successful, fully counted body write, whenever written_bytes >= next_threshold; start next_threshold at 1,048,576 and increment it by exactly 1,048,576 after emission
6. EOF at the existing PROGRESS_FINAL hook, before the existing hash gate
7. TERMINAL once after normal body/network finalization and error aggregation, before journal close, provided no earlier journal operation failed

The maximum byte snapshot count is 4,096 at 4 GiB. CHUNK remains 262,144 so one successful write crosses at most one new threshold. Actual `read1` may return one byte; this design does not assume full-sized chunks. There are six non-byte events, thus at most 4,102 frames. Enforce both record count and total-file-byte limits before any write. Exact cap including magic: 8 + 4,102 × (4 + 2,048 + 32) = 8,548,576 bytes. No timer-driven records and no catch-up or duplicate records. Failed or skipped lifecycle steps emit fewer frames, never synthetic successful events. If initial creation fails, no journal exists and no GET starts.

Each magic/frame is one checked write: an exact returned byte count is required. A short/throwing write poisons the journal; do not loop to finish it, write another frame, or retry. Call flush and fsync after magic and each complete frame; increment durable-in-process bookkeeping only after successful fsync. An unbuffered handle avoids concealed buffered retry writes; flush is still an explicit checked operation. Close exactly once with first-error preservation. fsync completion is the OS/filesystem durability acknowledgment, not a guarantee against device failure, directory-entry loss, or all power-loss scenarios. No new cross-platform directory-fsync guarantee is claimed.

## Crash granularity and acceptance tradeoff

Keep every original in-memory received/written counter update, incremental body hash update, per-chunk disk check and budget check. Replace only the progress persistence schedule. Original BEFORE_WRITE no longer persists every successful read; original AFTER_WRITE invokes the deterministic byte sampler. Thus a process crash can lose unsampled evidence of the current read or write. While successful sampled writes continue, the missing received-byte increment over the last snapshot is strictly less than 1 MiB + CHUNK, i.e. less than 1,310,720 bytes (including a read/write crossing the next threshold). This bound does not make an unsuccessful read's internally consumed bytes knowable and does not guarantee bounded elapsed time between records. A hanging/throwing read or write can leave counters incomplete or unknown. Sudden storage loss has weaker guarantees than ordinary process termination.

A reader stops at the first truncated, malformed, out-of-order, out-of-bounds or digest-invalid frame; it never scans forward or resynchronizes. A valid prefix is explicitly labeled crash evidence only, with counters as lower bounds, counters_complete false for the final attempt, and no reconstructed final hash, success, first error or GET count beyond what was recorded. A missing SENT record does not prove that no request was sent. An unsaved final error cannot be recovered by invention. A complete terminal journal frame alone cannot declare a pass or authorize static inspection.

This is an explicit reduction in process-crash diagnostic granularity, not a weakening of successful-download acceptance. If preserving every before/after-read snapshot is a hard requirement, this sampled design must not be approved. A compact per-chunk binary journal is not a minimal substitute: read1 may return single bytes, so the number of records cannot be bounded by BODY_MAX/CHUNK. A four-GiB body can cause billions of read calls; bounding such a log needs another policy and a larger redesign. The recommended tradeoff is bounded diagnostic sampling with unchanged exact final counters and strictly fail-closed gates.

## Terminal checkpoint, first error and success gates

After body/response/connection finalization, append TERMINAL if the journal is healthy. Then close the journal and record any close failure with existing record_error/close_preserving semantics. Never allow terminal checkpoint code to run while the journal handle is still owned/open; if close throws, treat closure as unconfirmed, do not retry close, return failed without creating the final checkpoint. This preserves a strict closed-before-checkpoint rule; the first failure may then be memory-only and the supervisor reports unknown details instead of inventing them.

Once journal closure succeeds, create `download-checkpoint.json` with `xb` exactly once. Use a dedicated final writer, not the replace path: bounded JSON serialization, exclusive open, exact checked write, flush, fsync, checked close, no rename. It carries the full final state plus journal format, actual frame count, last successfully fsynced frame digest, journal terminal-written flag and journal_close_completed true. It can persist a failed state after a distinct journal error; that is a separate final output, not a retry of the failed journal operation. The checkpoint-persisted flag is optimistic inside the serialized bytes, as today; it is meaningful only with independently confirmed exit and validation. Any final open/write/flush/fsync/close error sets in-memory checkpoint_persisted false, records error, returns nonzero, never retries and never runs static inspection. A physically parseable file after a failed fsync/close does not override the nonzero worker exit.

Preserve the earliest diagnostic unchanged, including operation, context, exception type, errno and winerror. Append subsequent journal/body/network/final-output failures to the existing eight-entry secondary list with truncation flag. Use explicit JOURNAL_OPEN/WRITE/FLUSH/FSYNC/CLOSE/READ and FINAL_CHECKPOINT_FLUSH/FSYNC operation enums, or equally precise fixed enums, with full restored_failure allowlist coverage. Never relabel the original error as generic JSON failure merely because persistence then failed. If persistence cannot save it, report that original details are unknown outside the worker.

The supervisor still waits for confirmed worker exit before opening either file. No added polling. A successful download requires the existing terminal-checkpoint schema, correct candidate/source identity, zero worker exit, no timeout/termination/error, exact nonzero equal received/written counts <= 4 GiB, counters_complete true, correct expected full-body SHA-256, response complete, body fsync and body close complete, expected artifact filename, plus successful journal closure and fully validated complete journal matching terminal checkpoint frame count/digest. A malformed/torn/missing journal, missing terminal frame, any contradiction, or trailing bytes makes success false even if terminal JSON looks successful. Static `worker_claim` and `can_inspect` must require the strengthened terminal evidence and supervisor success, never journal-prefix evidence. Failure reporting may parse the journal after confirmed exit even when final JSON is missing; preserve a terminal recorded error if available, and attach journal lower bounds separately.

## Resource, ownership and cleanup invariants

Keep BODY_MAX exactly 4 × 1,073,741,824; INCREMENT_MAX exactly 41 × GiB // 10 (4,402,341,478 bytes); FREE_START 8 GiB; FREE_KEEP 2 GiB; CONTROL_RESERVE 32 MiB; CHUNK 256 KiB. Keep 870-second active worker/900-second total download deadlines, existing watchdog behavior and stated Windows scheduling limitations. Journal fsync time consumes those same budgets; do not extend them, reset their start, or add retries. Add budget checks around journal/final persistence in addition to preserving every existing check; watchdog remains the bound on blocked I/O. Do not claim hard real-time termination guarantees.

DiskGuard continues counting all allocated files in work/out, including journal and checkpoint with cluster rounding. Check projected journal/header/frame growth before writes using the existing conservative projection and reserve. Actual total allocation, not the theoretical log cap, determines whether the operation is allowed. Do not subtract journal bytes from owned usage, raise a disk limit, repurpose the 32 MiB reserve, create a second journal, or duplicate the full log in report JSON. The journal's maximum logical size is 8,548,576 bytes; allocation can be higher by cluster rounding. A final checkpoint remains bounded by JSON_MAX (4 MiB). The reserved control budget is not permission to exceed existing disk gates; worst-cluster and near-limit tests must fail closed as needed.

Retain the one-GET latch, exact URL/expected hash, no redirects/proxies/retries, exclusive body creation, no extra GET/HEAD/Range probes, no installation/import/execution of downloaded code, and original static-analysis limits. Preserve attempt markers and consume a new identity-bound attempt for any later live run. Include existing or stale journal/final paths in preflight's already-used check. Never adopt or resume an old journal.

Retain the journal, final checkpoint, attempt markers and reports as bounded audit evidence on success or failure. Existing authorized partial-body cleanup only runs after confirmed worker exit and only for that attempt's recognized PART path. Do not add journal deletion, rotate logs, clean prior attempts, or delete a verified wheel. Disk pressure aborts rather than triggering extra deletion. Any later deletion of retained evidence requires separately established deletion authorization; deleting it also must never revive the consumed attempt. If exit/handle closure is unconfirmed, preserve the existing conservative no-cleanup behavior.
